## 1. 项目事实速查

### 1.1 定位

```text
面向电商数仓的多轮 Text2SQL 问数 Agent
```

系统只聚焦：

```text
闲聊
完整问数
多轮追问问数
```

不定位为通用 Agent 平台、完整 BI 报告系统或强 Multi-Agent 自主协作系统。

### 1.2 主体结构

- `mainAgent`：入口路由、多轮状态、追问改写、澄清、取消和失败重试；
- `askAgent`：关键词、召回、上下文、SQL 生成、校验、修正和执行；
- Qdrant：字段与指标语义候选；
- Elasticsearch：真实字段值；
- Meta MySQL：字段归属、指标口径与变体、表关系和粒度；
- `dw_v2`：最终业务查询。

### 1.3 关键限制

- 当前没有 LLM 自主选择 Repository 或数据库客户端；
- Repository 是节点中的服务依赖，不是暴露给模型的 Tool；
- 主流程由 LangGraph 预先编排；
- LLM 只在意图、改写、候选筛选、关键词扩写、SQL 生成和修正等局部环节决策；
- `select_metric_variant`当前使用确定性规则打分，不是 LLM 自主选择；
- SQL 校验主要保证安全、候选范围与可执行性，不能保证所有业务语义正确。

### 1.4 评测数字

```text
50 条单轮冻结题
12 组多轮，29 个对话回合，其中 23 个查询回合
三轮单轮结果准确率：98%、98%、94%
均值 ± 总体标准差：96.67% ± 1.89%
多轮整组正确率：11/12 = 91.67%
首版 SQL 执行成功：206/216 = 95.37%
最终 SQL 执行成功：216/216 = 100%
首版失败后正确恢复：10/10
```

# 第一轮：项目定位与 Agent 边界

## Q1. 请用一分钟介绍项目

**参考回答：**

> 这是一个面向电商数仓的多轮 Text2SQL 问数 Agent，基于开源 Text2SQL 底座进行业务收敛和二次开发。用户提出自然语言问题后，mainAgent 负责识别完整问数、追问和闲聊，并管理澄清、取消与失败重试；问数请求进入 askAgent，通过字段、指标和真实字段值的多源检索构造数仓上下文，再生成、校验、有限轮次修正并执行 SQL。项目主体是受约束的 LangGraph 工作流，在意图识别、追问改写、候选筛选以及 SQL 生成和修正环节使用局部 LLM 决策。最终通过 50 条单轮和 12 组多轮冻结集做结果级评测。

**关键词：** 场景、mainAgent、askAgent、多源检索、受约束工作流、结果级评测。

## Q2. 为什么这个项目可以叫 Text2SQL Agent？

**参考回答：**

> Agent 的最低定义不要求必须自由规划或自主调用工具，而是系统围绕目标维护状态，根据当前信息进行判断、行动并结合反馈推进任务。这个项目围绕“得到安全可执行且符合口径的 SQL 结果”这一目标，包含意图和追问判断、检索上下文、SQL 生成、校验反馈、修正与执行，因此可以称为 Text2SQL Agent。但它的自主性受约束，主体仍是固定工作流，不能包装成强自主 Agent。

## Q3. 项目中哪些部分是固定 Workflow？

**参考回答：**

> askAgent 从关键词提取、三路召回、合并、候选筛选、变体选择、上下文增强、SQL 生成、校验、修正到执行的节点顺序和分支空间由开发者预设；mainAgent 的入口、挂起事务处理、意图标签到节点的映射、澄清次数和重试次数也由代码固定。模型不能创建新节点、规划任意路径或跳出预设图。

## Q4. 哪些地方体现局部 Agentic？

**参考回答：**

> 局部 Agentic 主要体现在面对开放自然语言输入时，模型根据上下文作受约束判断，例如意图分类、追问能否独立解决、是否需要澄清、候选表和指标筛选、SQL 生成以及根据错误反馈修正 SQL。这些决策有语义不确定性，但决策空间和后续路由仍受代码约束。确定性的 pending 路由、指标变体规则打分和 SQL 校验分支本身不应包装成 LLM Agentic 决策。

## Q5. 意图识别为什么只能算局部 Agentic？

**参考回答：**

> 模型需要把开放的用户表达映射为 `chat`、`direct_query`或`followup_query`，具有语义判断能力；但输出标签和可达路径由开发者预设。模型输出标签后，是代码中的 Conditional Edge 将标签映射到具体节点。因此可以说模型影响去向，但不能说模型自主规划了执行流程。

## Q6. SQL 校验—修正循环算不算 Agentic？

**参考回答：**

> 它是一个受约束的反馈闭环。校验节点通过确定性规则和 EXPLAIN 产生错误反馈，条件边确定执行、修正或失败；修正节点中的 LLM 根据原 SQL、错误信息和生成上下文生成新 SQL。Agentic 特征主要来自模型利用反馈调整输出，而不是校验路由本身。循环最多修正三次，因此不是无界自主探索。

## Q7. 如果面试官说“这只是工作流，不是 Agent”，怎么回答？

**参考回答：**

> 我同意项目主体是固定工作流，不会把它包装成强自主 Agent；但工作流中存在面向开放输入的意图、追问、筛选、生成和修正决策，并且系统围绕问数目标维护状态、执行查询、接收校验反馈并调整。因此更准确的定位是受约束的 Text2SQL Agentic Workflow，固定流程保证查数安全和可追踪，局部 LLM 决策处理语义不确定性。

# 第二轮：检索、上下文与 LangGraph 工作流

## Q8. 为什么需要 Qdrant、Elasticsearch、Meta MySQL 和 dw_v2？

**参考回答：**

> 四者职责不同。Qdrant根据语义召回字段和指标候选；Elasticsearch根据用户关键词匹配数仓中的真实字段值；Meta MySQL提供权威字段归属、指标口径与变体、表关系和数据粒度；`dw_v2`只负责最终业务 SQL 的 EXPLAIN和执行。向量召回负责找候选，Meta负责纠正和补全权威关系，不能用一个系统简单替代全部职责。

## Q9. 为什么这不只是“RAG + 一次 SQL 生成”？

**参考回答：**

> 项目确实使用了 RAG 思想，因为模型需要检索外部字段、指标、字段值和元数据；但召回结果不会直接全部塞进提示词，而是经过合并、候选筛选、指标变体选择和上下文补全。生成 SQL 后还要进行安全、候选范围和 EXPLAIN 检查，根据反馈修正或失败，最后才执行。因此它是检索增强的 Text2SQL 工作流，而不是一次检索加一次生成。

## Q10. 普通 RAG、Agentic RAG 与当前项目有什么区别？

**参考回答：**

> RAG 的本质是检索外部知识增强生成，不限于文档。Agentic RAG进一步让系统根据当前信息决定是否继续检索、检索什么、使用哪个数据源以及何时停止。当前项目的字段、指标和值三路召回是固定流程，模型不能自主决定跳过某路或进行多轮自适应检索，所以它属于固定 RAG 增强的 Text2SQL 工作流，不应包装成强 Agentic RAG。

## Q11. askAgent 的完整链路是什么？

**参考回答：**

> `extract_keywords`提取查询关键词；字段、指标和值三路召回并行获取候选；`merge_retrieved_info`按表结构合并候选并补充相关字段和主外键信息；`filter_table`和`filter_metric`筛选必要表字段与指标；`select_metric_variant`通过确定性规则选择指标变体；`enrich_generation_context`补回指标和值涉及的字段、显式表关系并绑定字段值；`add_extra_context`增加当前时间和 SQL 方言；然后生成、校验、有限修正并执行 SQL。

## Q12. merge、filter、variant、enrich、extra 各解决什么问题？

**参考回答：**

> merge把分散召回结果按表字段结构组织，并结合Meta补全指标相关字段与主外键；filter让LLM从候选中保留与用户意图最相关的表、字段和指标；variant根据问题、候选表、商品上下文、粒度和默认变体做确定性打分；enrich补回过滤遗漏但被指标或值依赖的字段，加入显式连接关系并绑定真实值；extra只补充时间和数据库方言等生成环境信息。

## Q13. 为什么指标变体不用 LLM 自主选择？

**参考回答：**

> 指标变体涉及事实表粒度和固定业务口径，例如普通GMV默认基于订单表，出现商品、品牌或品类上下文时使用明细GMV。这个决策可以利用候选表、商品上下文、指标粒度和默认变体做可解释规则打分。相较让LLM自由选择，确定性规则成本更低、可追踪，也更适合口径要求严格的查数场景。

## Q14. 为什么使用 LangGraph，而不是纯 if-else？

**参考回答：**

> 两者在表达能力上没有本质差异，LangGraph也不会让模型更聪明。它的工程价值是统一管理State更新、显式定义节点职责和固定/条件边、支持并行召回与校验回边，并让日志、测试和故障定位能够围绕节点展开。节点和分支增多后，图结构比嵌套if-else更容易维护和观察。

# 第三轮：多轮状态管理

## Q15. mainAgent 的入口为什么不是所有请求都先做意图识别？

**参考回答：**

> 真实入口先执行`route_by_pending_query`。如果没有挂起事务才进入普通意图识别；如果正在澄清，则当前输入优先作为澄清答案进入追问改写；如果处于可重试状态，明确“重试”可以直接重新调用问数链路。这样避免把事务中的“直播渠道”“取消”“重试”等短输入误判为普通新问题。

## Q16. 完整新问题为什么不继承上一轮查询？

**参考回答：**

> 完整新问题本身已经包含足够指标和条件，继续继承历史容易把上一轮过滤条件污染到当前查询。只有被识别为追问时，系统才使用上一轮成功问题、精简`query_spec`和SQL进行改写。这样区分“会话历史存在”和“当前查询必须继承历史”两个概念。

## Q17. 追问改写使用哪些上下文？输出什么？

**参考回答：**

> 输入包含当前用户消息、上一轮成功问题、精简查询上下文、上一轮成功SQL以及可能存在的pending澄清信息。模型严格输出结构化状态，包括`resolved`、`independent`、`clarify`、`cancelled`或`chat`，并在需要时给出完整改写问题、候选问题或澄清问题。Pydantic负责验证，非法结构允许自动修复一次。

## Q18. 澄清生命周期是什么？

**参考回答：**

> 当追问信息不足时，改写结果返回`clarify`，系统创建`phase=clarifying`的pending事务，保存原消息、候选完整问题和澄清历史，并把澄清问题返回用户。下一轮输入优先填入pending并重新改写，不再做普通意图分类。最多允许两轮澄清，超限后要求用户重新提供完整问数。

## Q19. 澄清过程中闲聊或取消怎么处理？

**参考回答：**

> 澄清中的普通闲聊由改写模型返回`chat`，系统轻量回复并保留pending，用户仍可继续补充；明确取消可以由确定性短命令或改写状态识别，返回取消响应并在记忆更新阶段清除pending。对话消息仍可保留，但上一轮成功查询上下文不受影响。

## Q20. 失败重试如何工作？

**参考回答：**

> askAgent执行失败时，系统把已解析的完整问题保存为`phase=ready_to_execute`的pending，并记录是否可重试、错误和重试次数。用户输入“重试”后，代码先检查可重试性与最多两次的限制，再直接重新运行完整askAgent，不重复普通意图识别和追问改写。成功后清除pending并提交新的成功上下文。

## Q21. 为什么失败查询不能覆盖上一轮成功上下文？

**参考回答：**

> 追问改写依赖上一轮成功语义。如果失败请求覆盖成功上下文，用户下一轮追问会继承一个没有可靠结果的查询，形成错误传播。因此当前查询先在本轮State中运行，只有askAgent成功后才事务式提交`last_successful_query_context`；失败只更新pending重试信息，不替换上一轮成功上下文。

## Q22. State、SessionMemory和query_spec的边界是什么？

**参考回答：**

> State保存一次LangGraph调用中各节点流转的业务数据，图结束后本轮State不承担跨轮记忆；SessionMemory按会话保存历史消息、上一轮成功查询上下文和pending事务；`query_spec`是一次成功问数的精简结构化语义，包括完整问题、指标、表、过滤、维度、时间和SQL，用于追问改写和评测契约。结果行不保存进长期会话记忆，避免体积膨胀和旧数据污染。

# 第四轮：数仓口径与 SQL 可靠性

## Q23. 三张事实表的粒度是什么？

**参考回答：**

> `fact_order`一行一笔订单，适合订单数、订单GMV、客单价和支付用户数；`fact_order_item`一行一个订单商品明细，适合销量、品类GMV和件单价；`fact_refund`一行一次退款事件，适合退款金额、退款订单数和退款件数。区分粒度是为了避免事实混算和一对多Join造成重复统计。

## Q24. 五张维表分别提供什么？

**参考回答：**

> `dim_date`提供年、季度、月、周末和节日；`dim_region`提供大区、省份、城市和城市等级；`dim_product`提供商品、品类、品牌和价格带；`dim_member`提供会员等级、性别和年龄段；`dim_channel`提供渠道名称、类型和付费属性。地区、会员和渠道直接挂在订单表，商品挂在订单明细表，日期分别关联订单日期和退款日期。

## Q25. 常见指标如何计算？

**参考回答：**

> 订单GMV是`SUM(fact_order.order_amount)`，商品或品类GMV是`SUM(fact_order_item.item_amount)`；实付金额是`SUM(pay_amount)`；订单数是`COUNT(DISTINCT order_id)`；销量是`SUM(quantity)`；支付用户数是`COUNT(DISTINCT member_id)`；客单价是GMV除以订单数；件单价是明细金额除以销量；订单退款率是成功退款订单数除以有效订单数；件数退款率是成功退款件数除以有效销量。订单指标默认排除取消订单，退款指标默认只统计成功退款。

## Q26. 订单日期和退款日期如何选择？

**参考回答：**

> 订单数、GMV等订单事件指标使用`fact_order.date_id`；退款金额、退款件数和成功退款订单数使用`fact_refund.date_id`；订单退款率先按下单日期确定订单cohort，再统计其中最终发生成功退款的订单，当前口径不按退款日期再次过滤。因此2024下单、2025退款进入2025退款金额但不进入2025订单退款率；2025下单、2026退款则相反。

## Q27. 为什么双事实指标要分别聚合？

**参考回答：**

> 例如按品类同时统计商品GMV和退款金额，销售明细与退款事件粒度不同。直接INNER JOIN会过滤没有退款的销售明细，导致GMV偏小；一条明细存在多次退款时又会复制销售明细，导致GMV偏大。因此销售侧按订单日期、有效订单和品类先聚合`SUM(item_amount)`，退款侧按退款日期、成功状态和品类先聚合`SUM(refund_amount)`，最后按品类连接两个聚合结果。

## Q28. SQL校验包含哪些层次？

**参考回答：**

> 首先做程序化只读安全和结构检查，阻止多语句、危险写操作及不允许的表字段；然后通过`dw_v2`执行EXPLAIN验证数据库能否解析和规划；通过后才执行真实查询。校验结果写入State，由条件边决定执行、有限修正或失败。

## Q29. 哪些错误可以修正，哪些应该直接阻断？

**参考回答：**

> 模型格式残留、语法错误、未知字段、部分候选范围错误和EXPLAIN错误可以把具体反馈交给修正节点再生成；多语句、写操作或安全策略明确阻断的SQL不应让模型反复尝试绕过，而是直接失败。修正后的SQL仍必须重新经过完整校验。

## Q30. SQL校验不能保证什么？

**参考回答：**

> 它不能保证模型准确理解业务问题。一个SQL可能只读、字段合法、EXPLAIN通过并成功执行，但仍然使用错误指标变体、遗漏年份、混合下单和退款日期或错误分组。因此执行成功率不能替代结果准确率，关键业务语义仍需要Gold结果、`query_spec`契约和失败样本分析共同验证。

# 第五轮：评测与量化结果

## Q31. 评测使用的业务数据怎么来的？

**参考回答：**

> 使用的是本地合成电商数仓，不是企业生产数据。数据由固定种子的脚本生成，保证订单、明细和退款主外键一致，并设置地区、品类、会员、渠道和促销差异。评测快照包含3000笔订单、5069条订单明细、463条退款、100个商品、1000名会员、26个地区、7个渠道和912个日期，时间范围是2024年初到2026年上半年。

## Q32. 50条单轮和12组多轮怎么设计？

**参考回答：**

> 先根据数仓结构、指标口径和Text2SQL风险建立覆盖矩阵，再设计问题并确认当前数仓中可查询。单轮覆盖基础指标、过滤、时间、分组、TopN、多指标、指标变体、退款关联、双事实表以及0、空集和NULL；多轮覆盖条件替换和删除、指标追加、独立换题、澄清、澄清中闲聊、取消、时间替换和组合追问。正式集与开发测试分离并冻结，失败后不能针对题目调Prompt再沿用旧分数。

## Q33. Gold SQL和Gold结果如何产生？

**参考回答：**

> Gold SQL基于明确业务口径编制并独立于被测Agent输出；构建脚本先检查题目ID覆盖，再进行只读安全检查、MySQL EXPLAIN和真实执行，最后保存SQL、规范化结果行、行数和验证状态。Gold结果是经审核SQL在固定数据库快照上的执行结果，后续不会传给Agent，只在运行结束后用于评分。

**诚信边界：** 如果使用AI辅助编写，应说“AI辅助生成、结合口径逐条审核”，不能把另一份未经审核的模型输出直接称为Gold。

## Q34. 为什么比较结果，而不是比较SQL字符串？

**参考回答：**

> 同一个业务问题可以有多种等价SQL，例如日期可以使用日期维表或范围过滤，CTE和子查询也可能等价。字符串完全匹配会把正确的等价SQL误判为错误，因此项目比较执行结果。但结果相同也可能是数据巧合，所以严格任务准确率还会检查意图、工作流状态和`query_spec`中的指标及基础事实表契约。

## Q35. 结果比较器有哪些模式？

**参考回答：**

> `scalar`比较单个指标；`row`比较单行多个指标；`unordered`按关键维度对齐无序分组行集；`ordered`逐行比较TopN有序结果；`empty`要求返回零行；NULL则作为标量中的显式空值比较。金额默认允许0.01绝对误差，退款率使用0.0001，并把业务别名映射到规范列名，但渠道ID和渠道名称不会视为等价。

## Q36. 结果准确率和严格任务准确率有什么区别？

**参考回答：**

> 结果准确率只要求最终返回行与Gold等价；严格任务准确率还要求意图或追问路由正确、askAgent成功，并且`query_spec`满足声明的指标和事实表口径。例如S35三轮都得到正确数值，但`query_spec`仍记录为商品明细口径，结果准确率通过、严格任务准确率失败。

## Q37. `96.67% ± 1.89%`怎么计算？

**参考回答：**

> 三轮50条单轮结果分别通过49、49和47条，对应98%、98%和94%；平均值是96.67%，对这三个轮次准确率计算总体标准差得到1.89个百分点。它描述三轮模型运行的波动，不是置信区间，也不能外推为生产准确率。

## Q38. 多轮整组正确率为什么是91.67%？

**参考回答：**

> 每轮有12组多轮序列，要求一组中的查询、澄清、闲聊和取消等每个回合都通过，整组才通过。三轮都是11组通过、1组失败，因此每轮`11/12=91.67%`，三轮总体标准差为0。失败的是M12，第三回合“渠道改成App”被误判为需要澄清。

## Q39. SQL修正为什么是`95.37% → 100%`？

**参考回答：**

> 三轮共有219个查询评测，但M12第三回合三次都在路由阶段进入澄清，没有生成SQL，所以只有216个实际首版SQL。评测器从SSE中记录第一个`tool_sql`作为首版SQL，并独立做只读检查、EXPLAIN和执行；最终状态使用工作流返回结果。首版206条可执行，`206/216=95.37%`；最终216条全部可执行，且10次首版失败都恢复为正确结果，因此最终执行成功率100%。正式评测没有注入错误，这些是模型自然产生的首版错误。

## Q40. 主要失败案例和评测边界是什么？

**参考回答：**

> S29一轮返回渠道ID而非名称；S33一轮遗漏年份；S35结果正确但口径契约错误；S44和S45暴露订单日期与退款日期混合；M12把明确追问误判为澄清。比较器v1.1还修正过“成功退款金额”的列别名假阴性，只基于保存的原始结果重评分，没有重新调用模型。评测基于本地合成数据、固定模型Prompt和有限题集，只适合作为项目级回归和简历证据，不能证明任意数仓或生产环境泛化能力。

# 第六轮：个人贡献、局限与质疑

## Q41. 原项目已有能力与你的工作怎么区分？

**参考回答：**

> 原项目提供了基础Text2SQL问数链路。我在其上完成电商数仓和指标口径收敛，梳理多源检索与上下文边界，增加mainAgent多轮状态机，包括追问改写、澄清、取消、失败重试和成功上下文保护，并补充结果级评测与真实链路验证。实现过程中使用AI辅助编码，我主要负责需求拆解、业务规则、方案审核、调试、测试设计和验收，不把项目描述成完全从零手写。

## Q42. 你在项目中解决的最关键问题是什么？

**参考回答：**

> 一个关键问题是多轮追问不能简单拼接聊天历史，因为失败查询会污染后续语义。我把跨轮记忆收敛为上一轮成功问题、精简`query_spec`和成功SQL，并用pending管理澄清和重试事务，只有成功执行后才提交新的成功上下文。这样既支持条件替换和指标追加，又避免失败请求覆盖可靠历史。

## Q43. 为什么Repository调用不算LLM自主Tool Use？

**参考回答：**

> 当前Repository作为Runtime Context中的服务依赖，由预设节点确定性调用。模型不知道这些服务的工具名称、描述和参数协议，也不会输出工具调用请求或根据返回结果决定继续调用哪个工具。真正的LLM Tool Use需要把工具定义暴露给模型，由模型选择工具和参数，代码校验并执行后将结果反馈给模型形成闭环。

## Q44. 当前系统最容易失败在哪里？

**参考回答：**

> 一是召回缺失或字段值歧义会让后续上下文不完整；二是指标变体和双事实日期口径可能生成可执行但业务错误的SQL；三是多轮改写可能把明确追问误判为澄清；四是本地合成数据可能让错误SQL碰巧得到相同结果。当前通过Meta补全、确定性变体规则、SQL校验、成功上下文保护和结果级评测降低风险，但不能完全消除语义错误。

## Q45. 如果后续增强Agentic能力，会怎么做，风险是什么？

**参考回答：**

> 可以把字段、指标和值检索封装成受约束工具，让模型根据缺失信息选择数据源，并增加检索充分性判断或Human-in-the-loop审批；也可以让模型在候选范围内提出查询计划。但查数场景强调口径、安全和可追踪，自主空间扩大后会增加调用成本、延迟、不可复现决策、错误工具参数和绕过业务约束的风险，因此应保留白名单、结构化参数、轮次限制、状态记录和确定性校验。

# 2. 高频质疑的一句话回答

## “这只是套壳调用LLM。”

> 模型调用本身不是项目价值，核心在于数仓语义检索、权威元数据补全、多轮事务状态、指标粒度、SQL可靠执行和结果级评测；同时我会明确哪些代码来自开源底座和AI辅助，不用“自主智能”掩盖工程事实。

## “没有自主Tool Use就不算Agent。”

> 自主Tool Use是强Agent能力之一，不是Agent最低定义；当前系统围绕问数目标维护状态、进行局部语义决策、执行SQL并根据反馈修正，但自主性受限，所以定位为受约束Text2SQL Agent，而不是强自主Agent。

## “准确率96.67%，是不是已经能上线？”

> 不能。该结果只对应本地合成数仓、固定题集和当前模型环境，题量适合项目回归但不足以证明生产泛化；上线还需要真实业务问题、人工口径验收、权限与审计、监控和持续回归。

## “为什么不用强Agent自主规划？”

> Text2SQL查询步骤相对稳定，而错误SQL可能造成数据泄露、错误决策或资源浪费。固定主流程加局部LLM决策可以在语义理解和工程可控之间取得更合适的平衡。

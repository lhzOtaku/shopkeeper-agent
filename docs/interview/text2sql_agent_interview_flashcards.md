# 电商数仓多轮 Text2SQL 问数 Agent：20题核心背诵卡

> 目标：先用20题覆盖简历中第一项目的主要追问，再使用详细手册查漏。  
> 背诵方法：先记“关键词链”，再用自己的语言扩成30～60秒回答。不要逐字背稿。

## 使用规则

每张卡按三步学习：

```text
看问题，只看关键词复述
→ 对照30秒回答补漏
→ 记住“不要说”中的边界
```

建议分四次：

1. 卡1～5：定位与架构；
2. 卡6～10：检索和多轮；
3. 卡11～15：数仓与SQL；
4. 卡16～20：评测与贡献。

## 卡1：一分钟介绍项目

**问题：** 请介绍一下你的电商问数项目。

**关键词链：** 电商数仓 → mainAgent → askAgent → 多源检索 → SQL校验修正 → 结果级评测。

**30秒回答：**

> 这是一个面向电商数仓的多轮 Text2SQL 问数 Agent，基于开源底座进行业务收敛和二次开发。mainAgent负责完整问数、追问和闲聊路由以及澄清、取消和失败重试；askAgent通过字段、指标和真实字段值检索构造上下文，再生成、校验、有限修正并执行SQL。项目主体是受约束的LangGraph工作流，最后使用50条单轮和12组多轮冻结集做结果级评测。

**不要说：** 通用Agent平台、完整BI系统、强Multi-Agent、完全自主规划。

## 卡2：为什么可以叫Text2SQL Agent

**问题：** 这不是工作流吗，为什么还能叫Agent？

**关键词链：** 目标 → 状态 → 判断 → 行动 → 反馈 → 受约束。

**30秒回答：**

> 项目围绕得到安全可执行且符合口径的查询结果维护状态，包含意图和追问判断、外部知识检索、SQL生成、校验反馈、修正与执行，因此具备Agent的判断—行动—反馈闭环。但节点、路径和工具调用都由开发者预设，所以更准确的定位是受约束的Text2SQL Agentic Workflow，而不是强自主Agent。

**不要说：** Agent必须自主规划TODO或必须自主Tool Use；用了LangGraph所以更智能。

## 卡3：固定Workflow与局部Agentic

**问题：** 哪些流程固定，哪些地方有局部Agentic？

**关键词链：** 固定节点和分支 → 开放语义输入 → 局部LLM决策 → 代码路由。

**30秒回答：**

> 关键词、三路召回、合并、筛选、变体、上下文、生成、校验、修正和执行的节点及分支空间是固定的。LLM主要在意图分类、追问改写、候选筛选、关键词扩写、SQL生成和修正中处理开放语义；模型输出结构化结果后，由代码更新State并通过条件边路由。pending入口、指标变体打分和校验路由属于确定性代码。

**不要说：** 模型自己创建路径；校验节点是LLM自主决策；变体由LLM选择。

## 卡4：为什么使用LangGraph

**问题：** 为什么不用纯if-else？

**关键词链：** State → 节点职责 → 并行 → 条件边/回边 → 可观测与维护。

**30秒回答：**

> LangGraph不会提高模型能力，它解决的是工程编排。它统一管理State更新，显式划分节点职责，支持三路并行召回、条件分支和SQL修正回边，并让日志、测试和故障定位围绕节点展开。规模较小时if-else也能实现，但节点和状态增多后图结构更容易维护。

**不要说：** LangGraph让模型更聪明；if-else无法实现同样功能。

## 卡5：mainAgent和askAgent的边界

**问题：** 两个Agent分别负责什么？

**关键词链：** mainAgent管会话事务 → askAgent管一次问数。

**30秒回答：**

> mainAgent是入口层，负责pending事务优先路由、完整问数/追问/闲聊分类、追问改写、澄清、取消、失败重试和跨轮成功上下文保护。askAgent接收一个可独立执行的完整问题，完成检索增强、SQL生成、校验、有限修正和执行。mainAgent不规划askAgent内部节点，askAgent也不负责跨轮会话生命周期。

**不要说：** 两个Agent自主协作或互相通信规划；mainAgent是复杂规划Agent。

## 卡6：四个数据系统的职责

**问题：** 为什么同时使用Qdrant、ES、Meta MySQL和dw_v2？

**关键词链：** Qdrant语义候选 → ES真实值 → Meta权威关系与口径 → DW执行。

**30秒回答：**

> Qdrant根据语义召回字段和指标候选；Elasticsearch匹配数仓中真实字段值，帮助构造WHERE条件；Meta MySQL提供权威字段归属、指标变体、表关系和粒度；dw_v2负责最终EXPLAIN和查询执行。前两者偏召回，Meta负责权威补全，DW负责业务结果，职责不能简单互换。

**不要说：** ES召回指标；Meta MySQL只是另一个向量库；dw_v2用于元数据召回。

## 卡7：为什么不是简单RAG加SQL生成

**问题：** 这个项目和普通RAG有什么区别？

**关键词链：** 外部知识检索 → 合并筛选补全 → SQL生成 → 校验反馈 → 执行。

**30秒回答：**

> 项目使用RAG思想检索字段、指标、真实值和权威元数据，但召回结果不会直接全部塞给模型，而要合并、筛选、选择指标变体并补全表关系和字段值绑定。SQL生成后还要经过安全、候选范围和EXPLAIN检查，根据反馈修正或失败。因此它是检索增强的Text2SQL工作流，不是一次检索加一次生成。

**不要说：** RAG只能检索文档；三路固定召回就是强Agentic RAG。

## 卡8：askAgent主链路

**问题：** 一次问数经过哪些步骤？

**关键词链：** 关键词 → 三路召回 → 合并 → 筛选 → 变体 → enrich → extra → 生成 → 校验修正执行。

**30秒回答：**

> 系统先提取和扩写关键词，并行召回字段、指标和真实值；随后按表结构合并结果，筛选候选表字段和指标，通过确定性规则选择指标变体；再补回指标和值依赖字段、显式表关系和字段值绑定，并增加当前时间与SQL方言。最后生成SQL，经过校验后执行，或根据可修正错误进入最多三次的修正回边。

**不要说：** 每个节点都由LLM完成；enrich可以沿任意外键自动发现新表。

---

## 卡9：指标变体为什么使用规则

**问题：** `select_metric_variant`为什么不是LLM选择？

**关键词链：** 固定业务口径 → 候选表/商品上下文/粒度/默认变体 → 可解释打分。

**30秒回答：**

> 普通GMV和商品品类GMV可能分别使用订单和明细事实表，这属于固定业务口径。当前节点根据用户问题、候选表、商品上下文、指标粒度和默认变体进行确定性规则打分，选择最高分变体。相比LLM自由选择，这种方式成本更低、可追踪，也更适合口径严格的查数场景。

**不要说：** 变体由LLM自主决定；规则选择完全不会出错。

## 卡10：多轮追问如何工作

**问题：** 系统如何区分新问题、追问和挂起事务？

**关键词链：** pending优先 → 无pending再意图分类 → 追问改写 → resolved/clarify等状态。

**30秒回答：**

> 每次请求先经过pending路由：没有pending才做普通意图分类；正在澄清时，当前输入优先作为澄清答案；可重试事务收到“重试”时直接重新调用askAgent。普通追问会结合上一轮成功问题、精简query_spec和SQL改写成完整问题，并输出`resolved`、`independent`、`clarify`、`cancelled`或`chat`等结构化状态。

**不要说：** 所有输入都先做意图识别；代码自己理解用户语义；模型直接修改State。

---

## 卡11：澄清、取消与重试

**问题：** 信息不足或执行失败时怎么处理？

**关键词链：** clarifying最多2轮 → chat保留pending → cancel清除 → ready_to_execute → retry最多2次。

**30秒回答：**

> 信息不足时创建`phase=clarifying`的pending并返回澄清问题，下一轮回答直接进入改写，最多两轮；澄清中闲聊会轻量回复并保留pending，取消会清除事务。askAgent失败后保存`phase=ready_to_execute`的完整问题、错误和可重试状态，用户输入“重试”后最多重新执行两次，不重复普通意图识别和改写。

**不要说：** 所有取消都由固定关键词判断；失败后一定可重试。

---

## 卡12：State、SessionMemory与成功上下文

**问题：** 为什么失败不能覆盖上一轮成功查询？

**关键词链：** State管本轮 → Memory管跨轮 → query_spec是精简语义 → 成功后提交。

**30秒回答：**

> State保存一次图调用中的节点数据；SessionMemory按会话保存历史消息、上一轮成功查询上下文和pending；query_spec保存指标、表、过滤、维度、时间和SQL等精简语义。只有askAgent成功后才事务式提交新的成功上下文，失败只更新pending，否则下一轮追问会继承错误查询。完整结果行不写入长期记忆。

**不要说：** State等于长期记忆；LangGraph Checkpoint等于业务会话记忆。

---

## 卡13：三张事实表与核心指标

**问题：** 数仓事实表如何分工？

**关键词链：** 订单粒度 → 明细粒度 → 退款事件粒度。

**30秒回答：**

> `fact_order`一行一笔订单，用于订单数、订单GMV、客单价和支付用户数；`fact_order_item`一行一个订单商品明细，用于销量、品类GMV和件单价；`fact_refund`一行一次退款事件，用于退款金额、退款订单数和退款件数。区分事实粒度可以防止一对多Join后重复计算订单金额或混淆订单数与销量。

**不要说：** 划分事实表只是为了表不拥挤；销量等于明细行数。

---

## 卡14：订单日期与退款日期

**问题：** 不同退款指标的时间怎么选？

**关键词链：** 订单事件看下单日 → 退款事件看退款日 → 订单退款率先定订单cohort。

**30秒回答：**

> GMV和订单数按`fact_order.date_id`过滤；退款金额、退款件数和成功退款订单数按`fact_refund.date_id`过滤。订单退款率先按下单日期选出有效订单作为分母，再统计这些订单中最终成功退款的去重订单，当前口径不再限制退款年份。因此2024下单、2025退款进入2025退款金额但不进入2025订单退款率。

**不要说：** 所有退款相关指标都按退款日期；退款率分子可以脱离分母订单集合。

---

## 卡15：SQL校验与修正边界

**问题：** 如何保证生成SQL可靠？

**关键词链：** 只读/结构/候选范围 → EXPLAIN → 执行；可修正反馈 → 最多3次；语义不保证。

**30秒回答：**

> 候选SQL先做只读安全、结构和表字段范围检查，再通过dw_v2执行EXPLAIN，通过后才真实执行。语法、未知字段或EXPLAIN错误可以把原SQL、错误和生成上下文交给LLM修正，修正后必须重新校验，最多三次；多语句和危险写操作直接阻断。该机制保证安全和可执行性，但不能发现所有指标变体、日期口径和分组语义错误。

**不要说：** EXPLAIN通过等于业务正确；最终执行成功率100%等于结果准确率100%。

## 卡16：评测业务数据怎么来的

**问题：** 评测数据是真实业务数据吗？

**关键词链：** 本地合成 → 固定种子 → 主外键一致 → 业务规律 → 不外推生产。

**30秒回答：**

> 不是企业生产数据，而是固定种子脚本生成的本地合成电商数仓，保证订单、明细和退款主外键一致，并设置品类、渠道、会员和促销差异。评测快照有3000笔订单、5069条明细和463条退款，时间覆盖2024年初到2026年上半年。它适合项目回归，不能代表真实生产分布。

**不要说：** 真实企业数据、真实线上用户数据、完全随机数据。

## 卡17：题集与Gold怎么产生

**问题：** 50条单轮、12组多轮和标准答案怎么来的？

**关键词链：** 覆盖矩阵 → 冻结问题 → 独立Gold SQL → 安全/EXPLAIN/执行 → Gold结果。

**30秒回答：**

> 先根据数仓结构、指标口径和Text2SQL风险建立覆盖矩阵，设计50条单轮和12组多轮问题，并与开发测试分离冻结。每个查询问题有独立于被测Agent输出的Gold SQL，经业务口径审核、只读检查、EXPLAIN和dw_v2真实执行后保存标准结果。Gold不会传给Agent，只在运行结束后用于评分。

**不要说：** Gold是保存一次Agent成功输出；由另一个AI生成就自动可信；失败后针对正式题调Prompt还能沿用旧分数。

## 卡18：为什么比较结果，还要检查query_spec

**问题：** 为什么不直接比较生成SQL和Gold SQL？

**关键词链：** 等价SQL多种 → 比较结果 → 数据巧合风险 → 严格契约补充。

**30秒回答：**

> 同一个业务问题可以使用不同但等价的日期条件、CTE或子查询，字符串匹配会误判，因此项目比较执行结果。比较器支持标量、单行多指标、无序分组、有序TopN、空集和NULL，并处理别名与数值容差。但结果可能因数据巧合相同，所以严格任务准确率还检查路由、工作流成功和query_spec中的指标及基础事实表契约。

**不要说：** 结果相同就能证明SQL语义一定正确。

## 卡19：三个评测数字怎么算

**问题：** `96.67% ± 1.89%`、`91.67%`和`95.37%→100%`分别是什么？

**关键词链：** 49/50、49/50、47/50 → 11/12整组 → 206/216到216/216。

**30秒回答：**

> 三轮单轮结果分别是49/50、49/50和47/50，即98%、98%和94%，均值96.67%，总体标准差1.89个百分点。多轮每轮12组中11组全部回合通过，所以整组正确率91.67%。三轮共有219个查询评测，但M12第三回合三次未生成SQL，实际首版SQL为216个，其中206个可执行，修正后216个全部可执行，因此是95.37%到100%。

**不要说：** 1.89%是置信区间；SQL修正把业务准确率提升到100%。

**问题：** 当前系统有什么问题，你具体做了什么？

**关键词链：** 日期/口径/路由失败 → 合成数据边界 → 开源底座 → 多轮状态与评测 → AI辅助、本人审核验收。

**30秒回答：**

> 失败主要包括S29返回渠道ID、S33遗漏年份、S35结果正确但query_spec口径错误、S44和S45混合订单与退款日期，以及M12把明确追问误判为澄清。评测只代表本地合成数仓和固定环境，不能外推生产。原项目提供基础Text2SQL链路，我负责业务范围和指标口径收敛、多轮状态机、成功上下文保护、测试与结果级评测设计；实现使用AI辅助编码，我负责需求拆解、方案审核、调试和验收，不描述成从零手写。

**不要说：** 已达到生产可用；所有代码独立手写；评测证明通用泛化。

# 背诵验收

完成一组卡片后，不看文档回答：

```text
1. 一句话结论是什么？
2. 至少三个关键词是什么？
3. 能举哪个项目案例？
4. 哪句话绝对不能说？
```

评分标准：

- 8分：结论正确、事实完整、有边界；
- 7分：方向正确，但缺字段、案例或限制；
- 6分及以下：概念混淆、使用理想设计替代当前实现，或量化数字解释错误。

建议顺序：先完成卡16～19的评测部分，因为这是当前最薄弱且简历数字最容易被深挖的区域；通过后再从卡1顺序复习整个项目。

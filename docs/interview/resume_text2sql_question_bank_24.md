# 电商数仓多轮 Text2SQL 问数系统：24 道简历面试题库

> 适用岗位：中小厂 AI Agent / LLM 应用开发实习岗  
> 对齐范围：简历第一个项目，不延伸到“代码仓库智能体 Harness”  
> 编写依据：当前仓库源码、配置、Prompt 和冻结机制评测集  
> 回答长度：主问题 60～90 秒，单个追问 20～40 秒

## 使用方法

每道题按五部分组织：

1. **面试问题**：面试官最可能直接问出的形式；
2. **考察点**：面试官真正想判断什么；
3. **参考回答**：按“当前实现 → 为什么这样做 → 局限与改进”回答；
4. **递进追问**：从简历自然延伸的合理追问；
5. **容易说错**：需要避免的夸大、混淆或错误结论。

不要逐字背诵。最低要求是记住每题的结论、三个实现证据和一个边界。

## Q1. 请用一分钟介绍这个项目

**考察点**

能否用业务目标、核心链路、个人工作和结果构成完整闭环，而不是罗列技术名词。

**参考回答**

这是一个面向电商经营分析的多轮 Text2SQL 问数系统。用户可以直接询问 GMV、订单数、退款率等指标。系统先由 mainAgent 判断闲聊、完整问数还是追问；进入 askAgent 后，通过 LangGraph 编排关键词提取、字段/指标/字段值三路召回、候选过滤、指标变体选择、上下文增强、SQL 生成、校验、有限修正和执行。字段与指标语义候选来自 Qdrant，真实字段值来自 Elasticsearch，Meta MySQL 提供权威指标口径、表字段和 Join 关系，最终只在 DW MySQL 执行只读 SQL。我的工作重点是指标变体选择、结构化上下文增强、多轮追问状态和 SQL 可靠执行，并为这些机制设计了冻结评测。项目主体是固定工作流，局部由 LLM 完成语义判断和生成。

**递进追问**

- **这个项目中最棘手的矛盾是什么，你怎么处理？** 一边要提高召回率，避免漏掉指标、字段和值；另一边又不能把大量候选直接交给 SQL 模型。我把它拆成“高召回候选 → LLM 过滤 → 确定性补全 → SQL 范围校验”，让每层只解决一个问题，并用上下文机制评测验证补全前后变化。
- **你怎么证明它不是只能跑通一条 Demo？** 我没有只展示成功查询，而是分别构造稀疏上下文、多轮状态和 SQL 故障注入三类冻结集，验证指标变体、状态生命周期、危险阻断和错误修正；同时明确这些只能证明机制，不代表开放域准确率。
- **如果重新做一次，最先改变什么？** 我会更早建立端到端结果 Gold 和节点 Trace，让每次修改都能同时看到最终业务结果、中间召回和路由变化，避免项目后期才补评测证据。

**容易说错**

- 不要称为可以自由拆解任意任务的强自主 Agent。
- 不要说最终结果由 LLM 直接回答；结果来自 DW 执行。
- 不要把机制评测的 100% 说成开放域 Text2SQL 准确率 100%。

## Q2. 你在这个项目中具体完成了什么

**考察点**

个人贡献是否与简历一致，能否进一步落到模块、状态和评测证据。

**参考回答**

我的工作集中在四部分。第一，完善 askAgent 的受约束问数链路，让表和指标过滤后继续经过确定性指标变体选择与结构化上下文增强。第二，针对订单和商品明细两种分析场景设计指标变体规则，避免 GMV、订单数等指标在错误粒度上重复计算。第三，在 mainAgent 中增加基于上一次成功查询的追问改写、澄清、取消和失败重试，并用 pending_query 保护未完成事务。第四，增强 SQL 可靠性：增加只读、多语句、上下文表字段范围和 EXPLAIN 检查，修正后必须重新校验。最后，我把这些能力拆成上下文、多轮和 SQL 可靠性三套冻结机制评测，分别验证局部能力。

**递进追问**

- **举一个能证明你确实改过代码的问题。** 加入多轮后，失败查询如果直接覆盖最近上下文，下一轮追问就会继承失败状态。我把“最近成功查询”和“未完成事务”拆成 `last_successful_query_context` 与 `pending_query`，并把提交集中到 `update_memory`，只有 askAgent 成功且返回 query_spec 才替换成功上下文。
- **你评估过哪些更简单的方案，为什么没有采用？** 一种是直接把完整聊天历史交给问数链路，另一种是只拼接上一条消息。前者噪声和 Token 较大，后者无法区分失败、闲聊和澄清，因此最终选择精简成功上下文加 pending 生命周期。
- **修改是否带来了新问题？** 带来了状态分支和测试复杂度，所以我增加了澄清、取消、独立换题、重试成功和重试耗尽等序列契约；当前仍只有进程内记忆，多实例场景需要外部存储和锁。

**容易说错**

- 只描述功能，不说状态和验证方式，会显得像只看过演示。
- 不要声称所有底层组件和最初技术选型都是从零独立开发；回答以简历中的工作为边界。

## Q3. 一次完整问数请求是怎么流转的

**考察点**

能否从入口连续讲到结果，并区分 mainAgent 与 askAgent 的职责。

**参考回答**

请求先进入 mainAgent。没有 pending 事务时，系统进行三分类：闲聊进入 normal_chat，完整问题直接调用 askAgent，依赖历史的问题进入 rewrite_followup。追问被改写成可以独立执行的问题后再交给 askAgent。askAgent 先用 Jieba TF-IDF 抽取关键词，并行召回字段、指标和真实字段值；合并节点根据指标依赖和值绑定从 Meta 补候选字段和主外键；LLM 分别过滤表字段与指标；确定性规则选择指标变体；enrich 节点补变体依赖字段、强值绑定和候选表间显式 Join；随后加入当前时间和数据库方言，生成 SQL。SQL 通过 AST 安全与范围检查、MySQL EXPLAIN 后才执行；可修正错误进入有限回边，危险 SQL 直接阻断。成功后生成 query_spec，并由 mainAgent 更新成功上下文。

**递进追问**

- **并行召回最容易出现什么实现问题？你怎么避免？** 三个分支如果同时写同一个 State 字段会产生覆盖或需要 reducer。当前让字段、指标和值分别写入独立字段，等三个分支结束后由 `merge_retrieved_info` 统一合并和去重；表过滤与指标过滤也分别写自己的结果。
- **你排查链路问题时从哪里开始？** 先看每个节点的 progress 和 State 输出，确认关键词、三路召回、过滤前后、变体和 enrich 是否符合预期，再看 generation_context 和 SQL 校验记录。例如过滤条件遗漏时，先判断是 ES 未召回、LLM 过滤丢失，还是 enrich 没形成强绑定。
- **哪一段不能简单并行？** 变体选择必须等待表和指标过滤，enrich 又依赖已选变体；SQL 生成必须等待最终结构化上下文。强行并行会读取不完整状态。

**容易说错**

- 不要说表关系由向量数据库召回；当前由 Meta MySQL 按候选表查询。
- 不要说执行失败会回到 SQL 修正；当前修正回边由校验失败触发，run_sql 异常会结束本次 askAgent。

## Q4. 为什么称它为 Agent，而不是普通工作流

**考察点**

是否理解 Agent 的自主程度边界，能否避免为了包装项目而过度定义。

**参考回答**

更准确的定位是“固定 Text2SQL Workflow 主体、局部 LLM 决策增强的弱 Agentic 系统”。主流程、可用节点、最大修正次数和安全边界都由代码确定，这保证问数任务可审计。Agentic 部分体现在系统根据语义和运行状态选择入口路由、改写追问、过滤候选、生成 SQL，并根据校验反馈决定执行、修正还是阻断，形成状态—判断—行动—反馈闭环。没有让模型自由拆解任意目标或自主选择任意工具，是因为问数步骤稳定、业务口径和数据安全比自由度更重要。如果将来需要跨数据源分析或报告生成，可以在受控 Tool Registry 和预算约束下增加规划能力，但不会直接放开数据库操作。

**递进追问**

- **你有没有考虑让模型自由选择工具或规划步骤？为什么没做？** 评估过这种方向，但问数的核心步骤稳定，而且直接连接数据库，开放规划会增加漏校验、错误工具调用、延迟和审计难度，因此当前只在意图、过滤、生成和修正等语义节点使用 LLM。
- **这个系统哪里真正根据反馈改变了行为？** SQL 校验失败后会按错误类型进入修正、阻断或执行分支；多轮入口也会根据 pending 的阶段直接进入澄清改写或重试，而不是每次走同一条直线。
- **如果以后增强自主性，你会先开放什么？** 先增加受控的只读分析工具和明确预算，例如 Schema 查询或结果解释，并要求每次工具调用都经过白名单、超时和 Trace；不会先开放任意 SQL 或任意 Shell。

**容易说错**

- “用了 LangGraph 就是 Agent”不成立。
- 不要把 Repository 调用称为模型自主 Tool Calling；它是节点内部固定依赖调用。

## Q5. 为什么使用 LangGraph，而不是普通 if-else 或 while 循环

**考察点**

是否能把框架选型映射到真实图结构，而不是背“可视化、可扩展”。

**参考回答**

当前流程同时存在并行召回、并行过滤、条件路由和 SQL 修正回边，LangGraph 能用 StateGraph 把这些关系统一声明。每个节点只返回自己修改的状态字段，框架负责汇合依赖和推进边，便于查看节点职责、记录 Trace 和做节点契约测试。普通 if-else 当然也能实现，而且小流程可能更轻；但随着分支、回边和多轮状态增多，控制流会和业务逻辑混在一起。代价是需要设计 State/Context，理解状态合并语义，也会增加框架依赖。若流程始终很小、没有并行和恢复需求，我会优先普通 Python；当前图的复杂度已经足以让 LangGraph 的结构化收益大于成本。

**递进追问**

- **如果不用 LangGraph，你会怎么实现？遇到的维护问题是什么？** 可以用异步函数、`gather`、if-else 和 while 完成，但并行汇合、错误终态、回边计数和进度事件会分散在控制代码里。当前把路由函数、节点和边单独声明，测试时能直接验证拓扑与节点契约。
- **使用 LangGraph 后遇到的新难点是什么？** 必须明确每个字段由谁写、并行分支如何汇合，以及 State 与 Runtime Context 的边界。为避免覆盖，三路召回使用独立 State 字段，外部连接全部放 Context。
- **怎么验证修正回边不会死循环？** 路由函数读取独立的 `correction_count`，最多三轮；故障注入中专门设置持续返回错误 SQL 的案例，预期终态必须是 `correction_limit`。

**容易说错**

- 不要说 LangGraph 自动解决并发冲突；同一字段的合并仍需要明确定义。
- 不要说 if-else 无法实现，只能说在当前复杂度下维护成本更高。

## Q6. State、Context 和 Memory 分别保存什么，为什么要分开

**考察点**

是否理解一次图执行状态、外部依赖和跨轮会话状态的生命周期差异。

**参考回答**

askAgent 的 State 保存一次问数过程中会被节点读写的业务数据，例如 query、keywords、召回结果、table_infos、metric_infos、generation_context、SQL、校验记录和 rows；这些对象适合合并、记录和测试。Context 保存不会参与状态合并的运行依赖，包括 Qdrant/ES Repository、Embedding 客户端以及 Meta、DW Repository，避免把连接对象放进可序列化业务状态。Memory 跨多轮存在，保存消息、上一次成功查询的精简上下文和 pending_query。这样拆分是按生命周期和职责划分：State 属于单次执行，Context 属于执行环境，Memory 属于会话。当前 Memory 只在进程内，生产化需要外部存储和并发控制。

**递进追问**

- **如果把连接对象和业务数据都放进 State，会出现什么具体问题？** 连接对象不适合序列化、复制和状态合并，也会让节点测试必须创建真实外部资源。我把 Repository 和客户端放 Runtime Context，State 只保留可观察的业务中间结果。
- **你遇到的状态一致性难点是什么？** 成功上下文、澄清 pending 和执行重试的生命周期不同，如果在各节点直接修改 Memory，失败中途可能留下半提交状态。因此节点只生成 `pending_action` 或 ask_result，最后由 `update_memory` 统一提交。
- **当前拆分仍有什么缺陷？** MemoryStore 是单进程字典，没有持久化、版本控制和同会话锁；多 worker 或并发请求会产生丢失历史和覆盖更新。

**容易说错**

- 不要说当前已经实现 LangGraph Checkpoint/Resume；简历第一项目没有这一主张。
- 不要混淆 askAgent State 和 mainAgent 的跨轮 SessionMemory。

## Q7. 为什么同时使用 Qdrant、Elasticsearch、Meta MySQL 和 DW MySQL

**考察点**

能否说明四类数据源各自解决的问题，以及“候选来源”和“权威来源”的区别。

**参考回答**

四者职责不同。Qdrant 保存字段和指标的名称、描述、别名向量，用语义相似度解决用户表述与元数据名称不一致的问题；Elasticsearch 保存配置允许同步的真实字段值，用 IK 分词和 match 查询召回“女装、华东、直播”等文本值及其字段绑定；Meta MySQL 是权威元数据库，保存表字段、指标及变体、字段依赖和表关系，用于补全并约束候选；DW MySQL 保存真实业务数据，只负责读取环境信息、EXPLAIN 和最终查询。当前设计用专用组件换取清晰职责，但部署成本较高。小规模场景可以用 Elasticsearch 同时承担文本和向量检索，或用 PostgreSQL＋pgvector＋关系表合并存储。

**递进追问**

- **多套存储最难维护的是什么？你怎么处理？** 难点是同一份元数据在 Meta、Qdrant 和 ES 之间的一致性。当前由 `MetaKnowledgeService` 统一读取配置和 DW 信息，先写权威 Meta，再为字段/指标构建向量点、为允许同步的字段值建 ES 索引，避免各组件各自生成规则。
- **如果 Qdrant 返回指标 ID，但 Meta 查不到完整指标怎么办？** 不能凭 Qdrant payload 猜公式；该候选应被丢弃或让流程失败并告警。指标公式和依赖以 Meta 为权威，向量库只提供轻量候选。
- **你考虑过只用一个数据库吗？** 可以，小规模下用 ES 同时做全文和向量，或 PostgreSQL＋pgvector 合并权威数据与检索会更省运维；当前拆分是为了职责清晰，不代表所有场景都必须这样选。

**容易说错**

- 不要说 Qdrant 或 ES 返回结果就是最终真相，它们只是召回候选。
- 不要说四个系统缺一不可；这是当前选型，不同规模可以合并。

## Q8. 指标变体是什么，系统如何选择正确口径

**考察点**

是否真正理解订单粒度与商品明细粒度，以及为什么选择确定性规则。

**参考回答**

同一个业务指标在不同分析粒度下可能有不同公式。例如整体 GMV 可以从 fact_order 的 order_amount 聚合；按商品或品类分析时，应从 fact_order_item 的 item_amount 聚合，否则订单金额 Join 到多条明细后会被重复计算。系统先由 LLM 确定用户要哪个指标，再由确定性规则在该指标 variants 中选择口径。规则考虑明确的正反向表述、是否存在商品/品类上下文、候选表、变体 base_table、适用维度和默认口径。明确指令权重最高，商品上下文优先明细口径，没有商品上下文时优先订单口径。选择后会记录 selection_reason。这样比再调用一次 LLM 更稳定、低延迟且便于追查；局限是规则覆盖外的新表达需要维护，未来可用离线数据驱动调整权重或在低置信度时请求澄清。

**递进追问**

- **你是怎么发现指标口径会出错的？** 把订单表与明细表 Join 后，如果仍聚合订单总金额，一笔订单的金额会随着明细行重复。按商品或品类分析必须改用明细金额；订单数则需要对订单 ID 去重。这促使我把同一指标拆成订单和明细 variants。
- **为什么没有直接再调用一次 LLM 选口径？你比较了什么？** LLM 能理解语义，但会增加调用成本、延迟和波动，而且口径规则已有明确证据：用户显式要求、商品上下文、base_table 和适用维度。因此当前采用确定性硬筛选加评分，并记录 selection_reason；低置信度场景再引入澄清更合适。
- **规则冲突时怎么排查？** 先查看显式正反向提示是否触发，再看商品上下文来自问题词还是 ES 绑定，然后检查候选表与 variant 配置。机制集用四个订单口径和四个商品口径场景验证当前规则。

**容易说错**

- 不要说指标名称由变体节点选择；指标由过滤阶段确定，变体节点选择该指标的具体公式。
- 不要承诺规则覆盖所有业务口径。

## Q9. enrich_generation_context 具体补了什么，为什么过滤后还需要它

**考察点**

能否说清输入、补全依据、输出与能力边界。

**参考回答**

过滤节点的目标是从高召回候选中缩小范围，但 LLM 可能保留了业务表却漏掉公式字段、默认过滤字段或 Join 键。enrich 节点读取已选指标变体、过滤后的表字段和 ES 值召回。它从 selected_variant 的 relevant_columns 与 default_filters 提取必需字段，通过 Meta 补齐；只把用户问题中真实出现的 ES 命中转成强 value_binding，并补对应表字段；最后根据当前候选表集合查询 Meta 中的显式表关系，同时补关系两端字段。输出是包含 metrics、tables、value_bindings 和 join_relations 的结构化 generation_context。它不是通用 Schema 搜索器，只能沿指标依赖、强值绑定和已有候选表关系补全；如果必要字段既不在这些依赖中，也没有被前面召回，仍可能遗漏。

**递进追问**

- **你怎么发现过滤后的上下文不够？** 我用稀疏 State 构造机制场景，只提供时间、品类等种子字段。增强前 12 个场景合计只命中 102/220 个必要元数据，常见缺失是指标公式字段、默认状态字段和 Join 键，说明单靠过滤结果不能稳定生成 SQL。
- **你评估过什么更简单的补救办法？** 一种是把完整 Schema 直接塞回 Prompt，但这等于提前提供答案，也增加 Token 和混淆；另一种是重新跑召回，但无法区分召回和补全能力。最终选择沿 selected_variant、强值绑定和候选表关系做确定性补全。
- **最终怎么证明方案有效，而不是上下文变多了？** 对每个场景预先冻结必要表、字段、Join、值绑定和粒度集合，按 micro average 比较增强前后命中，结果从 102/220 到 220/220；这个结论只覆盖这些依赖路径，不外推到最终 SQL。

**容易说错**

- 不要说 enrich 会自动发现任意漏表；它只沿已有证据补充。
- 不要说它验证了最终 SQL 必然使用所有值绑定；当前主要是提供结构化提示。

## Q10. 多轮追问是如何实现的，为什么只保存成功上下文

**考察点**

是否理解意图、改写、pending 生命周期和成功记忆的一致性。

**参考回答**

mainAgent 先检查 pending_query，再决定是否进入普通意图分类。没有 pending 时，LLM 将输入分成 chat、direct_query 和 followup_query；追问节点读取上一次成功查询的精简上下文，将“那华南呢”改写成可以独立执行的完整问题。改写结果通过 Pydantic 严格约束为 resolved、independent、clarify、cancelled 或 chat。信息不足时建立 clarifying pending；执行失败且可重试时建立 ready_to_execute pending；取消或超过次数时清理。成功上下文只有 askAgent 真正成功并返回 query_spec 后才替换，失败查询不会污染它。这样第三轮追问仍能基于最近一次成功事实，而不是继承失败或半完成状态。代价是模型改写能力成为关键依赖，当前也只保留最近一次成功查询。

**递进追问**

- **多轮实现中你遇到的最难问题是什么？** 不是把两句话拼起来，而是失败、澄清、闲聊、取消和重试时应该更新哪份状态。尤其失败查询不能覆盖成功上下文，否则后续追问会建立在错误基础上。
- **你考虑或尝试过哪些上下文方案？为什么最终没用完整历史？** 只传上一条消息无法知道它是否成功，完整历史又会把闲聊、失败 SQL 和大量中间信息带给模型。最终只保存成功 query_spec 的精简字段，同时用 pending 单独管理未完成事务。
- **你怎么验证状态没有被错误覆盖？** 在重试耗尽序列中，先成功查询 2025 GMV，再让 2024 退款金额连续失败；每一轮都检查 pending 仍指向失败查询，而成功上下文始终保留第一轮，超过重试上限后只清 pending。

**容易说错**

- 不要说失败后完全没有状态变化；失败可能建立 retry pending，但不会覆盖成功上下文。
- 不要说当前支持长期记忆或跨进程会话恢复。

## Q11. SQL 在执行前经过哪些检查，哪些错误可以修正

**考察点**

是否区分安全阻断、业务范围检查和数据库解析检查。

**参考回答**

候选 SQL 先经过 SQLGlot AST 检查。系统清理代码块，要求只有一条语句，根节点必须是只读查询，并阻断 INSERT、UPDATE、DELETE、DROP、CREATE 等表达式；这类安全错误不可修正，直接结束。随后把 SQL 使用的物理表和字段与 generation_context 允许范围对比，发现上下文之外的表字段时作为可修正错误。静态检查通过后，DW Repository 执行 EXPLAIN，让 MySQL 实际解析语法、表字段和方言。可修正错误进入 LLM 修正，最多三轮，而且每次修正结果都必须重新经过 AST、范围和 EXPLAIN；修正为危险 SQL 或空 SQL 会再次被阻断。通过后才执行。局限是这些检查主要保证可执行性和范围，不保证指标口径、Join 语义和最终数值一定正确。

**递进追问**

- **为什么只做 EXPLAIN 不够，你补了哪几层？** EXPLAIN 可以发现语法或真实表字段错误，但数据库中存在的越界表仍可能通过，也不能阻止多语句和修改操作。因此在它之前增加 SQLGlot AST 单语句只读检查，以及 generation_context 表字段范围对比。
- **修正循环出现过哪些失控风险，你怎么验证？** 风险包括持续返回同一错误、修正成危险 SQL 和修正为空。评测分别注入这三种结果，验证前者到三次上限后停止，后两者重新校验时直接阻断，不能绕过安全层执行。
- **当前校验仍漏什么，你准备怎么补？** 允许范围内的错误 Join、漏过滤和错误聚合仍可能通过。下一步会从 AST 提取 Join、WHERE、GROUP BY 和聚合表达式，与显式关系、值绑定和 selected_variant 做契约比较。

**容易说错**

- 不要说 EXPLAIN 会执行完整查询并验证结果。
- 不要说当前能识别所有错误 Join 或所有业务口径错误。

## Q12. 三套评测分别怎么设计，简历数字代表什么

**考察点**

能否把评测对象、隔离方式、计算方法和结论边界一次讲完整。

**参考回答**

我没有只做一套端到端评测，而是按机制拆成三套，便于隔离变量和定位故障。第一套给定稀疏的种子表、字段、指标和召回值，真实运行指标变体选择与 enrich；12 个场景中需要选择多口径变体的 8 个全部正确，必要元数据按表、字段、Join、值绑定和粒度做 micro average，覆盖从 102/220，也就是 46.36%，提升到 220/220。第二套有 10 组多轮对话，askAgent 用确定性桩，专门检查意图、改写、pending 和成功上下文；6 个需改写回合全部通过，且每组所有回合都通过才计入 Sequence Accuracy，结果 10/10。第三套用 15 条预构造 SQL 验证校验路由：4 条危险 SQL 全部执行前阻断，15/15 到达预期终态，5 类真实可修正错误经 LLM 修正、重新校验和 DW 执行后 5/5 恢复。这些是冻结小样本机制指标，不代表开放域端到端准确率。

**递进追问**

- **为什么没有一开始就只做端到端评测？你遇到什么归因问题？** 端到端失败可能来自召回、过滤、变体、改写、生成、校验或数据库，单个最终结果无法说明哪个机制坏了。因此把需要验证的节点保留为真实能力，其他部分用固定 State 或桩隔离。
- **评测集本身出过问题吗？你怎么处理？** 机制集曾发现少量元数据名称需要纠正，没有直接覆盖旧 Gold，而是保留 v1、记录 corrections、生成 v2 manifest 和新 SHA-256，再把三套机制全部重跑。端到端比较器也曾因结果列别名出现假阴性，只修改比较器并基于已保存原始行重评分，没有重新调用模型。
- **怎么防止为了得到 100% 不断修改题目？** 题目、预期状态和 Gold 在运行前冻结，脚本启动时校验哈希且不写回 Gold；若 Gold 错误必须版本化修订并全量重跑，不能在同一版本中静默改答案。

**容易说错**

- 46.36% 的分子分母不要说反：输入命中 102，增强后 220，Gold 总量 220。
- 15/15 是预期终态路由正确，不是 15 条 SQL 都执行成功。
- 5/5 只统计 5 个 real_repair 案例。

## Q13. 为什么先高召回，再让 LLM 过滤，而不是直接把召回结果交给 SQL 生成

**考察点**

是否理解召回率、精度、Token 和结构化上下文之间的权衡。

**参考回答**

用户可能用“成交额、卖了多少、女装”等业务表达，单次精确检索容易漏掉字段、指标和值，因此前半段采用关键词扩展加多路高召回，目标是构造候选集。高召回结果会包含相似但无关的字段和指标，直接交给 SQL 模型会增大上下文、Token、延迟和混淆，所以分别用 LLM 在给定候选范围内过滤表字段与指标，禁止新增候选外对象。随后再通过确定性变体选择和 enrich 补回必要依赖。这个设计把 LLM 用在开放语义筛选，把业务公式和安全边界留给确定性程序。改进方向是为召回和过滤分别记录 Recall@K、Precision、候选规模和延迟，并在低置信度时澄清，而不是一味扩大 TopK。

**递进追问**

- **召回阶段最初容易出现哪两类问题？** 一类是切词或用户同义表达导致漏召回，另一类是扩大关键词后候选过多。当前保留完整问题并让 LLM 扩展关键词降低漏召回，再通过候选过滤控制噪声。
- **如果过滤模型误删了必要字段，你怎么定位和补救？** 对比过滤前后的 table_infos，判断字段是否曾经召回；指标依赖、默认过滤、强值绑定和 Join 键由 enrich 补回。若字段不属于这些确定性依赖，就需要补召回样例、调整索引文本或让用户澄清。
- **为什么不持续增大 TopK 解决漏召回？** TopK 变大会增加 Token、延迟和相似字段干扰。更合理的是分别统计各召回分支 Recall@K、过滤 Precision 和最终缺失类型，再针对性增加别名、索引文本或阈值策略。

**容易说错**

- 不要说前半段追求精准召回；它优先避免漏候选。
- 不要把 LLM 过滤说成安全边界，真正的表字段边界还要在 SQL Guard 校验。

## Q14. 为什么选择 Qdrant？有没有考虑 Milvus、pgvector、FAISS 或 Chroma

**考察点**

是否能基于当前规模和职责讨论替代方案，而不是把某个向量库说成绝对最优。

**参考回答**

当前 Qdrant 用于两类轻量语义召回：字段和指标分别放在独立 collection，向量为 1024 维，使用余弦距离，并在 payload 中保留可还原的元数据。选择它的原因是专注向量检索、API 和 Python 异步客户端直接、支持持久化和 payload，适合本项目本地部署。它不是唯一选择。若元数据规模不大且已有 PostgreSQL，pgvector 可以减少一个基础设施；Milvus 更适合大规模、分布式向量场景，但当前会偏重；FAISS 适合单机实验，但持久化、过滤和服务治理要自己补；Chroma 上手快，适合原型，但当前更看重独立服务和明确集合管理。真正选型应比较召回率、P95 延迟、内存、运维和过滤需求，而不是只看流行度。

**递进追问**

- **实际接入 Qdrant 时最容易遇到什么故障，当前怎么恢复？** 共享异步客户端可能出现连接异常。Repository 会尝试创建临时新客户端重新查询，Embedding 也有相同的 fresh-client 兜底，并限制最大次数；指标召回在向量结果为空或部分关键词失败时还会用 Meta 文本匹配补充。
- **你怎么决定当前 0.6 阈值和 Top20 是否合理？** 当前是固定工程参数，不能声称已经最优。更严谨的做法是用冻结查询集画 Recall@K、误召回率和候选规模曲线，再结合下游过滤准确率和延迟选择参数。
- **如果改成 pgvector 或 Milvus，迁移重点是什么？** 需要重建 1024 维索引、迁移 payload 和去重逻辑，并重新跑召回与下游评测；不能只替换客户端后假设效果不变。

**容易说错**

- 不要声称实际做过所有候选数据库的基准测试；当前是基于职责和规模的工程选择。
- 不要说向量库能保证业务口径正确。

## Q15. 为什么真实字段值使用 Elasticsearch，而不是也放进 Qdrant

**考察点**

能否区分语义对象召回与真实枚举值匹配，并讨论一体化替代方案。

**参考回答**

字段和指标通常需要解决同义表达，所以使用向量相似度；真实字段值则更强调词面证据和可解释绑定，例如“华东”必须绑定到具体 table_id.column_id，而不是找到语义相近但实际不存在的值。当前 ES 对配置为 sync 的字段真实值建立索引，value 使用 IK 分词，其他字段用 keyword 保存结构绑定，通过 match 查询返回 ValueInfo。这样适合中文枚举值、短语和倒排检索，也方便保留真实值来源。替代方案包括 MySQL LIKE、ES 的向量能力、OpenSearch，或者统一进带全文能力的数据库。数据量很小时 MySQL 前缀或倒排表更简单；如果希望减少组件，ES 也可以同时承担向量和文本检索。当前双引擎职责清晰，但增加了部署、同步和一致性成本。

**递进追问**

- **值召回中最难处理的情况是什么？** 同一个词可能是多个字段的真实值，例如既像品类又像商品名。当前 ES 会返回带 table_id 和 column_id 的多个 ValueInfo，enrich 只把原问题中真实出现的值作为强绑定，但最终选择仍可能有歧义。
- **你尝试或比较过哪些替代方案？** MySQL LIKE 对小数据简单，但中文分词、相关度和扩展性较弱；把真实值全部向量化能处理模糊语义，却可能把不存在的相近值当真值；当前用 ES 倒排匹配保留词面证据，后续可增加上下文打分或显式澄清。
- **怎么控制索引膨胀和敏感值泄露？** 不是所有字段都同步，只有 Meta 配置中 `sync=true` 的字段进入 ES。生产中还应增加高基数字段限制、脱敏、权限和增量同步审计。

**容易说错**

- 不要说 ES 只能做关键词搜索或 Qdrant 只能做向量搜索；讨论的是当前职责划分。
- 不要说 ES 命中就一定要写进 WHERE；当前只有原问题中真实出现的值才进入强绑定。

## Q16. Embedding 模型用了什么，为什么选它，如何判断是否应该更换

**考察点**

是否知道真实配置，并能用评测而不是主观印象说明模型选型。

**参考回答**

项目使用本地部署的 `BAAI/bge-large-zh-v1.5`，通过 Hugging Face Text Embeddings Inference 服务暴露接口，输出 1024 维向量。字段和指标会把名称、描述和别名分别向量化成多个检索入口，查询关键词使用同一模型生成向量。选择它主要因为项目以中文业务语义为主，BGE 中文模型成熟、可本地部署，避免外部 API 成本和数据出域。这里不能说它一定优于 bge-m3、m3e、text2vec 或商业 Embedding，因为当前没有做完整横向实验。若要改进，我会冻结字段/指标查询集，对候选模型比较 Recall@K、MRR、延迟、吞吐、内存和最终过滤命中率，再决定是否更换；模型变化时还要重建向量索引并同步修改维度配置。

**递进追问**

- **接入 Embedding 时遇到的工程约束是什么？** 模型输出维度必须与 Qdrant collection 一致，当前都是 1024；模型更换后不能继续复用旧索引。另外本地 TEI 启动和连接可能失败，所以客户端初始化、健康检查和有限重试都要独立处理。
- **为什么不把名称、描述和别名拼成一段再向量化？** 拼接简单，但多个语义入口可能互相稀释。当前分别建点，任意入口命中后通过 payload 还原同一对象并按 ID 去重；代价是点数增加。
- **你有没有比较过其他模型？如果没有怎么回答？** 当前没有完成正式多模型 Benchmark，所以只能说明选择依据，不能声称最优。改进会用字段/指标 Gold 比较 bge-m3、较小 BGE 或商业模型的 Recall@K、MRR、延迟和资源。

**容易说错**

- 不要说模型名直接传给 LangChain 客户端；运行时客户端连接本地 TEI 地址，具体模型由服务配置加载。
- 不要声称做过未实际完成的多模型 Benchmark。

## Q17. Pydantic 在项目里解决了什么问题，为什么提示词约束还不够

**考察点**

是否知道 Pydantic 的真实落点，以及格式正确与语义正确的边界。

**参考回答**

Pydantic 主要用在两类边界。API 层用 QuerySchema 和 ChatSchema 把 JSON 请求转换成类型化对象；mainAgent 对 LLM 的意图和追问改写结果使用严格模型，设置 extra=forbid，并用字段和模型级校验保证 status 与 resolved_query、clarification_question 等字段组合一致。提示词只能要求模型按 JSON 输出，但模型可能多字段、缺字段、空字符串或状态互相矛盾，所以输出还要解析和校验；第一次失败后还可以进行一次格式修复。Pydantic只能保证结构契约，不能保证模型把“华东”改成“华南”的业务语义一定正确，因此还需要机制评测和状态断言。后续可把 askAgent 的更多 LLM 输出也统一成严格 Schema，并记录验证失败率。

**递进追问**

- **模型输出曾经可能出现什么问题，当前怎么恢复？** 可能返回代码块包裹 JSON、未知字段、空 reason，或者 status=resolved 却没有 resolved_query。当前先清理代码块并解析，再由 Pydantic 做字段和跨字段校验；首次失败后把原输出和错误交给一次修复调用，再次失败才保留 pending 并返回错误。
- **为什么只靠 Pydantic 仍会得到错误改写？** 它只能证明结构合法，例如 resolved_query 非空，不能证明年份、指标和过滤条件继承正确。因此多轮评测还要检查 required/forbidden concepts、pending 和成功上下文变化。
- **如果扩大 Pydantic 使用范围，你会先改哪里？** 优先把表过滤、指标过滤和关键词扩展从宽松 JSON parser 收敛到严格 Schema，并监控解析失败率；SQL 本身仍应用 AST，而不是用 Pydantic 验证语义。

**容易说错**

- 不要说 Pydantic 能保证输出内容正确。
- 不要说所有 askAgent 节点输出都经过 Pydantic；当前主要是 API 与 mainAgent 的严格模型输出。

## Q18. 为什么使用 SQLAlchemy 和 Repository，而不是在节点里直接拼 SQL

**考察点**

是否理解连接池、Session 生命周期、持久化模型和业务节点解耦。

**参考回答**

项目同时访问 Meta 和 DW 两套 MySQL，使用 SQLAlchemy 异步 Engine、AsyncSession 和 sessionmaker 管理连接池与请求级 Session；FastAPI 依赖层创建 Repository，再注入 Service 和 LangGraph Context。Repository 封装“如何查库”，例如 Meta Repository 负责查询指标变体、字段、主外键和表关系，DW Repository 负责 EXPLAIN 和执行，节点只表达业务步骤。这样便于替换数据源、Mock 测试、统一资源释放，也避免每个节点重复建立连接和拼接查询。直接 SQL 在少量固定查询里更轻，当前 Repository 内也使用了参数化 text SQL 和 ORM；如果项目很小，不必为了模式而模式。后续可进一步限制动态表名、增加事务边界、查询超时和只读数据库账户。

**递进追问**

- **如果在每个节点里直接创建连接和写 SQL，会遇到什么问题？** 连接建立、释放、异常处理和结果转换会重复，节点测试也必须依赖真实数据库。当前 Engine 在 lifespan 初始化，请求级 Session 由依赖注入管理，Repository 统一查询细节，节点只保留业务逻辑。
- **你比较过 ORM 和原生 SQL 吗？为什么两种都保留？** 元数据实体的增删查和映射适合 ORM；EXPLAIN、执行以及部分简单固定查询用 `text()` 更直接。Repository 的价值不是强制全部 ORM，而是统一边界、Session 和映射。
- **这个分层有没有带来额外复杂度？** 有，Manager、Repository、Mapper、Service 层较多。若只有单库和几个查询会偏重；当前同时连接 Meta/DW，并需要脚本构建和运行时读取，所以分层便于复用和 Mock。

**容易说错**

- 不要说 SQLAlchemy 自动保证业务 SQL 安全；候选 SQL 仍需 SQL Guard 和数据库权限。
- 不要说 Repository 完全消除了 SQL；它只是集中封装。

## Q19. 为什么使用 FastAPI 和 SSE，为什么不用 WebSocket

**考察点**

是否能从当前交互模式解释技术选型，而不是泛讲性能。

**参考回答**

FastAPI 负责请求 Schema、异步接口、依赖注入和应用生命周期管理。启动时统一初始化 Qdrant、Embedding、ES 和两套 MySQL 客户端，请求时只创建必要的 Session 与 Repository。问数链路包含多次检索和模型调用，耗时较长，所以接口通过 SSE 持续推送节点 running/success、SQL、结果和错误，让前端知道流程进度，而不是等待一个长请求后一次返回。当前交互是“前端提交一次问题，后端单向推送事件”，SSE 基于普通 HTTP，重连和调试更简单；WebSocket 适合高频双向通信、客户端持续控制或协同场景，当前收益不大。局限是流开始后难以修改 HTTP 状态码，异常也只能包装成 SSE 事件；生产化还需心跳、断线重连和事件 ID。

**递进追问**

- **为什么项目需要流式进度，解决了什么真实体验问题？** 问数要经过多次检索和 LLM 调用，一次性响应时用户无法判断系统正常运行还是卡死。节点通过 writer 输出 running/success/error，Service 转成 SSE，让前端展示当前步骤。
- **SSE 接入后遇到的异常处理难点是什么？** 响应头发出后不能再改成普通 500，所以 QueryService 和 ChatService 必须把异常规范化为 SSE error 事件；生产化还需心跳、事件 ID 和断线重连，避免前端把网络断开误判为正常结束。
- **如果要支持中途取消，你会怎么改？** 为每次执行生成 task_id，保存取消令牌并在节点边界检查；如果需要高频双向控制再使用 WebSocket，而不是为了取消一个动作直接重构全部通信。

**容易说错**

- 不要说 SSE 是双向协议。
- 不要把 SSE 当成缩短后端执行时间；它改善的是反馈体验和可观测性。

## Q20. 模型、Embedding、向量库和 SQL 修正的重试为什么要分开

**考察点**

是否能区分基础设施瞬时故障、模型输出故障和业务修正循环。

**参考回答**

这些重试解决的问题不同，不能共享一个计数器。LLM 调用使用带超时的指数退避，关键词扩展、过滤和改写通常有限重试，SQL 生成与修正也有自己的调用重试；Embedding 和 Qdrant 连接异常会尝试临时新客户端恢复；SQL 业务修正由 LangGraph 回边控制，最大三轮；多轮会话中的“重新执行上一条查询”又是 pending 层面的执行重试，当前上限两次。如果把它们混在一起，前两次模型超时可能错误消耗 SQL 修正预算，导致本来可修正的业务错误提前失败。改进方向是统一错误分类、熔断、超时预算和 Trace，把 retryable、non-retryable、safety-blocked 分开，并避免每层重试叠加造成总延迟失控。

**递进追问**

- **你遇到或预防的典型重试失控是什么？** 如果 LLM、Embedding、Qdrant、SQL 修正和用户执行重试共用计数，前两次连接超时就可能耗尽业务修正机会；如果每层都无限重试，又会形成重试风暴和超长尾延迟。因此每层使用独立次数和超时。
- **为什么 Qdrant/Embedding 失败不能直接返回空列表？** 空列表表示“确实没有候选”，异常表示“检索没有完成”。把异常吞掉会让后续以不完整上下文生成 SQL。当前记录失败关键词并有限恢复，指标还能用 Meta 文本检索补充；权威 Meta 不可用时应失败。
- **如果生产环境仍频繁超时，下一步怎么做？** 先通过 Trace 区分模型、网络和服务端耗时，再加全链路 deadline、熔断和退避抖动；降级必须声明能力损失，不能默默给出可能错误的结果。

**容易说错**

- 不要把“LLM API 重试次数”和“SQL 修正轮数”混为一谈。
- 不要承诺当前已经实现完整熔断器；现有主要是超时、有限重试和部分临时客户端兜底。

## Q21. 你的指标几乎都是 100%，是不是测试集太简单或为了简历画靶

**考察点**

能否正面承认小样本限制，同时说明冻结机制和指标仍然有什么证据价值。

**参考回答**

这个质疑成立一部分：三套机制集规模分别只有 12 个上下文场景、10 组多轮对话和 15 个 SQL 案例，覆盖不可能代表真实世界。它们的价值是验证已声明机制在冻结契约下是否运行，并作为后续回归基线，而不是证明系统泛化率。为避免运行后改答案，Gold 在运行前冻结，清单记录 SHA-256，评测脚本不写回 Gold；每个指标也有明确分母，例如 8/8 只统计需要多口径选择的场景，15/15 只表示到达预期终态。改进需要扩充真实用户问题、异常类型和多模型多次运行，并增加从自然语言到 DW 结果等价的端到端评测和人工错误分析。面试中我会主动把“机制通过率”和“系统准确率”分开。

**递进追问**

- **你真的遇到过 Gold 或评测器错误吗？怎么处理？** 机制 Gold 有三处元数据命名纠正，因此保留 v1，新增 corrections 和 v2 manifest，并重新跑全部机制；端到端结果比较器也曾漏识别退款金额别名，只基于保存的原始结果重评分，没有重新调用模型或修改题目。
- **如何区分代码回归、模型波动和外部服务故障？** 固定 Gold 后多次运行并看节点 Trace：稳定在同一节点以同样方式失败更像回归；同样输入有时成功有时失败更像模型波动；明确超时、连接异常则归为服务故障。
- **下一轮扩充评测最优先加什么？** 增加真实用户表达、值歧义、错误 Join、复杂时间口径和高风险 SQL；LLM 节点要多次运行并报告均值、方差和失败类型，而不是只报告最佳一次。

**容易说错**

- 不要为了维护数字否认测试集小。
- 不要说 SHA-256 能保证 Gold 本身正确；它只能保证运行时没有被悄悄修改。

## Q22. SQL 通过白名单和 EXPLAIN，为什么仍可能得到错误业务结果

**考察点**

是否理解语法正确、安全和业务正确是三个不同层级。

**参考回答**

白名单只检查 SQL 使用的表字段是否在本次 generation_context 中，EXPLAIN 只证明数据库可以解析执行；二者都不能证明业务语义正确。SQL 可能使用允许的表字段，却选错指标变体、漏时间或状态过滤、Join 条件错误、把退款日期和订单日期混用，甚至因为一对多 Join 产生重复聚合。当前结构化指标公式、默认过滤和值绑定能降低这些风险，但校验节点还没有完整验证 Join 是否来自显式 relation、强值绑定是否被 SQL 使用、聚合粒度是否匹配。改进可以用 SQLGlot AST 提取 Join、WHERE、GROUP BY 和聚合表达式，与 selected_variant、value_bindings 和 join_relations 做契约检查；最终仍要用冻结 DW 的结果等价评测验证业务正确性。

**递进追问**

- **举一个校验通过但业务错误的具体例子。** 按品类统计 GMV 时，表字段都合法，但如果 Join 明细后仍聚合订单总金额，同一订单会按明细行重复；或者退款金额使用订单日期而不是退款日期，EXPLAIN 也能通过。
- **你准备怎样检查 Join，而不是只说“加强提示词”？** 用 SQLGlot AST 提取每个 Join 两侧表字段和条件，规范化后与 generation_context.join_relations 对比；不在显式关系中的 Join 先打回或进入人工/模型复核，再补聚合粒度与默认过滤契约。
- **为什么不能强制 SQL 使用全部值绑定？** ES 可能为同一个词召回多个字段绑定，强制全部使用会生成错误的 AND 条件。更合理的是确认至少使用一个与所选表和语义一致的绑定，冲突时评分或澄清。

**容易说错**

- 不要说 AST 检查能彻底解决所有业务语义。
- 不要说只读查询出错“最多只是结果不准”；慢查询、越权读取和数据泄露仍是风险。

## Q23. 当前规模很小，同时部署 ES 和 Qdrant 是否过度设计

**考察点**

能否批判自己的选型，并根据规模给出简化方案。

**参考回答**

从当前教学数据量看，确实存在过度设计。拆成 Qdrant 和 ES 的好处是职责清晰：一个验证语义向量召回，一个验证中文真实值倒排检索，也更接近未来独立扩展；代价是多两个服务、数据同步、一致性、监控和故障面。若重新面向小厂 MVP，我会优先评估两种简化方案：一是 Elasticsearch 同时保存文本、结构 payload 和 dense_vector；二是 PostgreSQL＋pgvector，把权威元数据、值索引和向量放在同一数据库。只有当向量规模、并发、过滤或扩展需求证明专用向量库有收益时，再拆出 Qdrant。技术选型不是越多越高级，应由召回质量、延迟、成本和运维能力共同决定。

**递进追问**

- **如果让你现在删掉一个组件，你会怎么选？** 小规模 MVP 会先评估让 ES 同时承担真实值全文检索和字段/指标 dense_vector，或把全部迁到 PostgreSQL＋pgvector；选择依据是现有团队维护能力和检索评测，而不是个人偏好。
- **你怎么判断什么时候值得拆出专用向量库？** 当向量规模、并发、过滤复杂度或向量检索 P95 已经成为单引擎瓶颈，并且压测证明 Qdrant 带来可量化收益时再拆；否则双写和故障面可能不划算。
- **双引擎带来的数据不一致怎么发现？** 构建时记录 Meta 对象数、Qdrant point 数和 ES value 数，抽样验证 payload 与权威 ID；生产中还要有版本号、增量同步状态和重建任务告警。

**容易说错**

- 不要为了维护选型而说任何规模都必须双引擎。
- 也不要反过来说双引擎完全没有价值；重点是当前收益是否覆盖运维成本。

## Q24. 如果把系统部署给多个用户，最先要补哪些生产能力

**考察点**

是否认识到 Demo 可运行与生产可用之间的差距，并能按风险排序。

**参考回答**

第一优先级是会话一致性和数据库安全。当前 MemoryStore 在单进程内，多个 worker 无法共享记忆，同一 session 的并发请求也可能互相覆盖，所以需要把成功上下文和 pending 迁移到 Redis 或数据库，增加版本号、过期时间和按 session 锁。数据库账户应强制只读，并补查询超时、行数与资源限制，避免只靠 SQL 语法检查。第二优先级是可观测与韧性：统一 request/session/trace ID，记录各节点延迟、召回候选、模型重试、SQL 校验终态，增加健康检查、熔断和告警。第三是效果闭环：收集真实问题和人工反馈，扩充回归集，监控路由、召回、结果正确率和成本。最后再考虑长期记忆、报告生成或更强规划能力，不能先扩自主性再补安全。

**递进追问**

- **多 worker 部署后最先会出现什么故障，你怎么定位？** 同一 session 的下一轮可能落到另一个进程，读不到上一轮 Memory，于是把追问当成新问题。可以在日志中用 session_id 对比不同 worker 的路由和 memory_update，再确认进程内存储导致状态割裂。
- **同一用户同时发两条消息会怎样，最终方案是什么？** 两个请求可能读取同一旧上下文并先后覆盖成功记忆或 pending。生产中应使用 Redis/数据库持久化，加 session 级分布式锁或乐观版本号，并明确串行语义和超时释放。
- **如果只给两周，为什么先补这些而不是增加报告 Agent？** 会话一致性、只读权限、查询资源限制和 Trace 直接影响正确性与数据安全；报告生成属于能力扩展，应在基础链路可控、可恢复、可观测之后再做。

**容易说错**

- 不要声称当前已经支持多进程会话一致性。
- 不要只回答“上 Kubernetes、加缓存”；先说明具体故障和数据一致性方案。

# 统一回答原则

- 先给结论，再讲实现证据，最后主动说一个边界；
- 只说当前代码真实存在的能力，把未来方案明确标为“如果继续改进”；
- 技术选型不要说“最好”，要说“在当前约束下为什么合适”；
- 机制评测不要外推成端到端泛化能力；
- 被追问细节时优先回到数据流：输入是什么、状态怎么变、输出给谁、失败怎么走。

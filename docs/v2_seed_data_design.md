# v2 电商数仓造数规则设计稿

这份文档是 v2 落地的第四步：在表结构和指标口径确定之后，设计一套有业务规律、可验证、适合问数和分析的数据生成规则。

造数不是简单随机插入数据。对问数 Agent 来说，造数至少要满足三件事：

```text
表之间主外键能对上。
指标结果符合业务常识。
数据里有明显规律，后续分析才有内容可说。
```

如果数据完全随机，系统虽然能查出数字，但回答“为什么华东 GMV 高”“哪个渠道质量更好”时就没有分析价值。

## 1. 造数目标

v2 数据要服务于这些能力：

```text
自然语言问数
指标口径验证
SQL 多表 Join
TopN 排名
退款率分析
渠道对比
会员分层分析
后续轻量 data_analysis
```

所以数据需要覆盖：

```text
时间差异
地区差异
商品品类差异
会员等级差异
渠道差异
退款差异
促销峰值
```

## 2. 推荐数据规模

第一版不要造太大，够评测和演示即可。

建议规模：

| 表名 | 推荐规模 | 说明 |
| --- | --- | --- |
| dim_date | 2024-01-01 到 2026-06-30 | 覆盖去年、今年、季度、月份、618 |
| dim_region | 20-40 行 | 覆盖大区、省份、城市、城市等级 |
| dim_product | 200-500 行 | 覆盖品类、品牌、价格带 |
| dim_member | 5000-20000 行 | 覆盖会员等级、年龄段、新老客 |
| dim_channel | 6-8 行 | App、小程序、直播、广告、自然流量等 |
| fact_order | 50000-120000 行 | 一行一笔订单 |
| fact_order_item | 100000-300000 行 | 平均每单 1-3 个商品明细 |
| fact_refund | 5000-20000 行 | 按 5%-15% 左右退款率生成 |

如果本机性能一般，可以先用小规模：

```text
fact_order: 30000
fact_order_item: 70000
fact_refund: 4000
```

后续稳定后再放大。

## 3. 时间范围设计

建议日期范围：

```text
2024-01-01 到 2026-06-30
```

为什么这样选：

```text
当前项目运行日期是 2026 年，用户说“去年”时可以落到 2025 年。
覆盖 2025 全年，方便做季度、月份、双11分析。
覆盖 2026 上半年，方便做“今年”“近30天”等表达。
```

日期维表要标记特殊活动：

| 时间 | festival_name | 业务含义 |
| --- | --- | --- |
| 2025-01 下旬到 2025-02 上旬 | 春节 | 食品、礼品、家居增长 |
| 2025-06-01 到 2025-06-18 | 618 | 全品类促销峰值 |
| 2025-11-01 到 2025-11-11 | 双11 | 全年最大峰值 |
| 2025-12-12 | 双12 | 小促销峰值 |
| 2026-06-01 到 2026-06-18 | 618 | 今年促销峰值 |

周末也要标记：

```text
is_weekend = 1
```

用于后续测试：

```text
周末 GMV 是否高于工作日？
```

## 4. 地区规则

地区维表建议覆盖这些大区：

```text
华东
华南
华北
华中
西南
西北
东北
```

每个大区放几个城市，例如：

| 大区 | 示例城市 | 城市等级 | 业务权重 |
| --- | --- | --- | --- |
| 华东 | 上海、杭州、南京、苏州 | 一线/新一线/二线 | 高 |
| 华南 | 广州、深圳、佛山、厦门 | 一线/新一线/二线 | 高 |
| 华北 | 北京、天津、青岛、石家庄 | 一线/新一线/二线 | 中高 |
| 华中 | 武汉、长沙、郑州 | 新一线/二线 | 中 |
| 西南 | 成都、重庆、昆明 | 新一线/二线 | 中 |
| 西北 | 西安、兰州、乌鲁木齐 | 新一线/二线/三线 | 中低 |
| 东北 | 沈阳、长春、哈尔滨 | 二线 | 中低 |

造数规律：

```text
华东、华南订单量更高。
一线和新一线城市客单价更高。
西北、东北订单量略低。
华南直播渠道占比略高。
华东 App 和自然流量占比更高。
```

这样后续可以分析：

```text
华东 GMV 高，是订单数和客单价共同拉动。
一线城市客单价高于二线城市。
```

商品一级品类建议：


每个一级品类下面设计二级品类：

| 一级品类 | 二级品类示例 | 价格带 | 退款倾向 |
| --- | --- | --- | --- |
| 数码 | 手机、耳机、平板、智能手表 | 中价/高价 | 中 |
| 服饰 | 女装、男装、鞋靴、箱包 | 低价/中价 | 高 |
| 食品 | 零食、饮料、粮油、礼盒 | 低价/中价 | 低 |
| 美妆 | 护肤、彩妆、香水 | 中价/高价 | 中 |
| 家居 | 收纳、厨具、清洁、床品 | 低价/中价 | 中低 |
| 运动 | 运动鞋、运动服、健身器材 | 中价/高价 | 中 |
| 母婴 | 奶粉、纸尿裤、玩具 | 中价 | 中低 |
| 图书 | 教辅、文学、经管、童书 | 低价 | 低 |

造数规律：

```text
食品销量高，但客单价低。
数码销量低，但 GMV 高。
服饰销量高，退款率也高。
美妆复购较强，客单价中等偏高。
家居在春节前有增长。
运动在 618 和双11有明显促销增长。
```

商品价格规则：

```text
低价：10-100
中价：100-800
高价：800-8000
```

注意：

```text
商品标价 list_price 是维表价格。
订单明细 item_amount 根据 list_price、quantity 和折扣生成。
```

| 金卡 | 10%-15% | 客单价较高 |

年龄段建议：


```text

```

渠道建议：

| channel_name | channel_type | is_paid | 业务规律 |
| --- | --- | --- | --- |
| App | 自有渠道 | 0 | GMV 稳定，客单价中高 |
| 小程序 | 自有渠道 | 0 | 订单量稳定，客单价中等 |
| 直播 | 内容渠道 | 0 | 销量高，退款率高 |

| 信息流广告 | 付费渠道 | 1 | 新客多，退款率中高 |

| 社群 | 私域渠道 | 0 | 客单价高，用户质量好 |

```text
社群渠道铂金/金卡会员占比更高，客单价高。

自然流量退款率最低。
```

## 9. 订单明细生成规则

每笔订单生成 1-3 条订单明细，少数订单可以 4-5 条。

建议分布：

```text
1 个商品：60%
2 个商品：25%
3 个商品：10%
4-5 个商品：5%
```

每条明细生成：

```text
product_id
quantity
item_amount
discount_amount
pay_amount
cost_amount
```

数量规则：

```text
普通商品 quantity 多为 1-3
食品、日用品 quantity 可以更高
数码高价商品 quantity 通常为 1
```

金额规则：

```text
item_amount = list_price * quantity
discount_amount = item_amount * discount_rate
pay_amount = item_amount - discount_amount
cost_amount = item_amount * cost_rate
```

折扣规则：

```text
普通日 discount_rate: 0%-10%
618 discount_rate: 10%-25%
双11 discount_rate: 15%-35%
直播渠道 discount_rate 略高
社群渠道 discount_rate 略低
```

成本率规则：

```text
食品：60%-75%
数码：75%-90%
服饰：40%-60%
美妆：35%-55%
家居：50%-70%
```

第一版不一定做毛利指标，但 `cost_amount` 能为后续扩展预留空间。

## 10. 订单金额一致性

这是造数时最重要的约束之一。

订单主表金额必须由明细汇总得到：

```text
fact_order.order_amount = SUM(fact_order_item.item_amount)
fact_order.discount_amount = SUM(fact_order_item.discount_amount)
fact_order.pay_amount = SUM(fact_order_item.pay_amount) + shipping_amount
```

不要让订单金额和明细金额对不上。

否则用户问：

```text
各品类 GMV
```

和：

```text
整体 GMV
```

可能会出现无法解释的差异。

注意：

```text
整体 GMV 推荐用 fact_order.order_amount。
商品/品类 GMV 推荐用 fact_order_item.item_amount。
```

两者在全量有效订单上应该基本一致。

## 11. 订单状态规则

订单状态建议分布：

```text
completed：70%-80%
paid：10%-15%
partial_refunded：5%-8%
refunded：2%-5%
cancelled：3%-8%
```

促销期间可以略提高：

```text
partial_refunded
refunded
```

直播渠道和服饰品类退款相关订单更多。

指标默认排除：

```text
cancelled
```

但退款表只和实际发生退款的订单关联。

## 12. 退款生成规则

`fact_refund` 一行一次退款事件。

退款生成来源：

```text
从 fact_order_item 中按概率抽取明细生成退款。
```

退款概率由这些因素决定：

```text
商品品类
渠道
订单状态
促销活动
```

品类基础退款率：

```text
服饰：12%-18%
美妆：7%-12%
数码：5%-9%
运动：6%-10%
家居：4%-8%
母婴：3%-6%
食品：1%-3%
图书：1%-2%
```

渠道修正：

```text
直播：+4%-8%
信息流广告：+2%-4%
搜索广告：+1%-2%
自然流量：-1%-2%
社群：-1%-2%
```

促销修正：

```text
618：+1%-3%
双11：+2%-5%
```

退款状态分布：

```text
success：80%-90%
processing：5%-10%
rejected：5%-10%
```

退款原因建议：

```text
尺码不合适
质量问题
七天无理由
物流慢
描述不符
买错了
价格波动
```

退款金额规则：

```text
refund_quantity <= order_item.quantity
refund_amount <= order_item.pay_amount
```

大多数退款可以全额退款，少数部分退款。

## 13. 需要保留的确定性

为了评测稳定，造数脚本必须使用固定随机种子。

建议：

```text
RANDOM_SEED = 20260702
```

这样每次重新生成数据，核心结果不会乱变。

评测集里如果写了预期结果，就不会因为重新造数而失效。

## 14. 数据质量校验

造数脚本完成后，要自动打印或执行这些校验 SQL。

### 14.1 主外键完整性

检查订单外键是否都存在：

```sql
SELECT COUNT(*)
FROM fact_order fo
LEFT JOIN dim_date dd ON fo.date_id = dd.date_id
WHERE dd.date_id IS NULL;
```

其他外键同理。

### 14.2 订单金额一致性

检查订单金额和明细汇总差异：

```sql
SELECT COUNT(*)
FROM fact_order fo
JOIN (
  SELECT order_id, SUM(item_amount) AS item_total
  FROM fact_order_item
  GROUP BY order_id
) t ON fo.order_id = t.order_id
WHERE ABS(fo.order_amount - t.item_total) > 0.01;
```

### 14.3 基础指标 sanity check

至少输出：

```text
订单数
GMV
销量
支付用户数
退款金额
订单退款率
各地区 GMV
各渠道 GMV
各品类销量
各品类退款率
```

这些结果要符合预设业务规律。

## 15. 预期业务结果

造数完成后，希望能看到这些大致规律：

```text
华东、华南 GMV 排名前二。
一线城市客单价高于二线和三线。
数码 GMV 高但销量不是最高。
食品销量高但 GMV 不一定最高。
服饰品类退款率最高或接近最高。
直播渠道销量高，但退款率也偏高。
社群渠道客单价较高。
铂金会员客单价和人均消费最高。
618、双11出现明显销售峰值。
```

这些规律就是后续分析系统可以解释的内容。

## 16. 对评测集的影响

造数规则确定后，评测集可以围绕这些问题设计：

```text
统计 2025 年第一季度各地区 GMV
查询 2025 年销量最高的前 5 个商品
统计各渠道订单数、GMV 和退款率
按会员等级统计客单价和人均消费
查询退款率最高的前 5 个品类
统计 618 期间各品类销量
对比华东和华南 GMV
```

评测时可以检查：

```text
SQL 是否走对表
指标是否用对字段
结果是否符合预期规律
```

## 17. 对造数脚本的要求

后续脚本建议分步骤生成：

```text
1. 清空并重建 dw_v2
2. 写入 dim_date
3. 写入 dim_region
4. 写入 dim_product
5. 写入 dim_member
6. 写入 dim_channel
7. 生成 fact_order 和 fact_order_item
8. 基于订单明细生成 fact_refund
9. 执行数据质量校验
10. 打印核心指标摘要
```

脚本应该支持配置数据规模：

```text
--orders 50000
--members 10000
--products 300
--seed 20260702
```

第一版也可以先在脚本里写默认值，后续再加命令行参数。
